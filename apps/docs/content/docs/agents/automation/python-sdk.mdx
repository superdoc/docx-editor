Use the Python SDK when application code already knows which document operation to run. This guide accepts every
tracked change in a DOCX and writes the result to a separate file.

## 1. Install the Python SDK

SuperDoc supports Python 3.9 and newer:

```bash
python -m pip install superdoc-sdk
```

The package installs the matching SuperDoc CLI companion automatically. You do not need Node.js or a separate CLI
installation. Published companions support macOS on Apple Silicon and Intel, Linux on ARM64 and x64, and Windows on x64.

## Reuse one client across many operations

One `SuperDocClient` owns one SuperDoc host process. `connect()` (or entering the context manager) starts that process once. Every `open()` adds a document session inside the same process, and every method on a document handle is one request to it. The SDK never starts a process per operation.

A client created per operation pays the whole cold path every time: process start, engine load, and for a collaboration document the room connect and initial sync. That cost is the same for a read, a search, or a comment, so it dominates any workflow that issues many small operations. Hoist the client and the open out of the per-operation path:

```python
from superdoc import SuperDocClient

# Once per service, or once per collaboration room you serve.
with SuperDocClient() as client:
    document = client.open(
        {
            "doc": "contract-123",
            "collaboration": {
                "providerType": "hocuspocus",
                "url": "wss://collaboration.example.com",
                "documentId": "contract-123",
            },
        }
    )
    try:
        # Many times per agent turn. Each call reuses the open session.
        info = document.info({})
        matches = document.query.match(
            {"select": {"type": "text", "pattern": "termination"}, "require": "all"}
        )
    finally:
        # When the room or the service shuts down.
        document.close({})
```

The same shape applies to `AsyncSuperDocClient`; only the `await` keywords change.

Typical cost of each lifecycle for a 53-operation agent turn on a mid-sized document. Both SDKs drive the same host process over the same protocol, so the numbers apply equally to Python:

| Lifecycle                                | Median per call | Whole turn |
| ---------------------------------------- | --------------- | ---------- |
| New client per operation                 | ~460 ms         | ~24 s      |
| One client, open and close per operation | ~140 ms         | ~8 s       |
| One client, one open document            | ~40 ms          | ~3 s       |

What that lifetime means in practice:

- **A handle is a session.** Open a document once and keep the handle for as long as the workflow needs it. One client can hold several open documents; each handle is its own session.
- **One host runs one request at a time.** Operations on the same client queue. For parallel throughput across documents, run a small pool of clients and lease one per in-flight workflow.
- **Restart is automatic, sessions are not.** If the host process exits, the next request starts a new one and every previously open handle is gone; reopen the document.
- **Refs expire, node ids do not.** A `query.match()` ref is bound to the revision that produced it and stops resolving after any mutation. Block `nodeId` values stay stable across edits, so target follow-up work with `{"kind": "block", "nodeType": ..., "nodeId": ...}` and re-run `query.match()` only when you need a text range.

### Batch many operations into one request

Two document-level batches collapse several operations into one request:

- `document.mutations.apply(plan)` commits several text or formatting steps as one atomic transaction. Selector targets re-resolve before each step, so you do not re-search between them. See [Mutation plans](/document-api/mutation-plans).
- `document.plan.execute({"entries": [...]})` runs a list of arbitrary operations in one request. Each entry is its own transaction, so a failure partway through keeps the earlier entries committed.

For example, anchor a batch of comments in a single request instead of one request per comment:

```python
result = document.plan.execute(
    {
        "entries": [
            {
                "operationId": "comments.create",
                "input": {"target": {"text": quote}, "text": note},
            }
            for quote, note in review_notes
        ]
    }
)

# plan.execute reports a failed entry in "failure" rather than raising. An
# ignored result is an ignored batch: it stops at the first hard failure, so
# later entries never ran.
failure = result.get("failure")
if failure:
    raise RuntimeError(
        f"comment batch stopped at entry {failure['entryIndex']} "
        f"({failure['operationId']}): {failure['message']}"
    )
```

<Callout variant='warning' title='Tracked-change ids need the per-call path'>
  A `{"kind": "trackedChange", "trackedChangeId": ...}` comment target does not resolve inside a `plan.execute` entry on
  the default CLI-backed host. `track_changes.list` returns host-stable ids, and the translation back to engine ids runs
  as a hook on the top-level `comments.create` call, which plan entries bypass. Anchor comments to tracked changes with
  individual `document.comments.create` calls instead.
</Callout>

## Use the asynchronous client

Use `AsyncSuperDocClient` when the surrounding application already runs an event loop. Its document methods mirror the
synchronous client and are awaited:

```python
import asyncio

from superdoc import AsyncSuperDocClient


async def main():
    async with AsyncSuperDocClient() as client:
        document = await client.open({"doc": "./contract.docx"})
        try:
            info = await document.info({})
            print(info["counts"])
        finally:
            await document.close({"discard": True})


asyncio.run(main())
```

## Open a token-authenticated collaboration document

Pass a Hocuspocus or y-websocket token with the document's open request:

```python
document = await client.open(
    {
        "doc": "./contract.docx",
        "collaboration": {
            "providerType": "hocuspocus",
            "url": "wss://collaboration.example.com",
            "documentId": "contract-123",
        },
    },
    collaboration_auth={"type": "token", "token": user_token},
)
```

The credential is separate from the collaboration profile and command-line arguments. It applies to the provider
created for this open request. Per-open token authentication is not supported for Liveblocks or the standalone
document host.
