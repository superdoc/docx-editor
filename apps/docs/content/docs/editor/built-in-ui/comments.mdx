Comments are enabled by default. Provide the current user so new comments keep the correct author; without one, they
are credited to `Default SuperDoc user` (see [Set the user](/editor/configuration#set-the-user)). Then choose how the
comments UI adapts to the Editor width. For the thread lifecycle and what gets saved, start with
[Comments](/editor/comments).

## Try the comment workflow

Expand the Editor and click `September 30, 2026` to open its comment. Add a reply, then use the controls above the document:

1. Change **Layout** between Auto, Sidebar, and Inline to compare how the comment surface uses the Editor width.
2. Change **Actions** to Read. Your reply remains, but you cannot add another. Restore Write or Resolve to reply again.
3. With **Actions → Resolve**, choose the checkmark on the thread. Click `September 30, 2026` again to see its
   **Resolved** status, then choose **Reopen comment**.

Changing either configuration reloads the current DOCX because these are startup options. Thread changes remain; the
open comment and selection reset. The demo changes only the document in this browser. Your application saves those
changes by exporting the DOCX through the same flow you built in [Load and save](/editor/load-and-save-documents).

## Configure comments

Choose a group, then choose a field. Each entry shows its type, default, and a configuration fragment you can copy.

<CommentsConfigReference />

Use `layout: 'auto'` to switch between sidebar and inline threads according to the available width. Use
`interaction.comments.level: 'write'` when people may participate in a thread but your application keeps the final
resolve decision.

The comment level does not control tracked-change decisions. Configure those in
[Track changes](/editor/track-changes).

These options change browser interaction; they are not an authorization boundary. Enforce document access and comment
permissions in a trusted backend.

For the decision path across comment levels, `permissionResolver`, and backend checks, see
[Interaction and permissions](/editor/interaction-permissions).

## Open the composer from your toolbar

An **Add comment** button in your own toolbar can open the same composer as SuperDoc's floating comment tool. Call
`superdoc.ui.comments.openComposer()` with text selected. The comment is created only when the person submits it.

```ts
const button = document.querySelector<HTMLButtonElement>('#add-comment')!;
// Keep the document selection when the button is pressed.
button.addEventListener('mousedown', (event) => event.preventDefault());
button.addEventListener('click', async () => {
  const result = await superdoc.ui.comments.openComposer();
  if (!result.ok) console.warn('Could not open the comment composer:', result.reason);
});
```

`openComposer()` resolves `{ ok: false, reason }` without opening anything when nothing is selected
(`range-selection-required`), comments are read-only (`document-readonly`), the built-in comments UI is off
(`operation-unavailable`), or the Editor is not ready (`not-ready`). Call `superdoc.ui.comments.closeComposer()` to
discard an unsaved draft; it is safe when no composer is open. Calling it while `openComposer()` is still pending
cancels the open, which then resolves `{ ok: false, reason: 'operation-unavailable' }`.

To create the comment from your own text field instead, use `ui.comments.createFromSelection()` or
`createFromCapture()` from the [custom comments guide](/editor/custom-ui/comments).

## Show every comment and change in your panel

`superdoc.addCommentsList(element)` renders a list of every comment and tracked change in an element you provide. It
returns `true` when it mounts the list, and `false`, mounting nothing, for a viewer or when comments are turned off.
`superdoc.removeCommentsList()` removes the list.

`comments-list-change`, or `onCommentsListChange` when creating the Editor, reports `{ isRendered: true }` when the
list is mounted and `{ isRendered: false }` when it is removed:

```ts
const panel = document.getElementById('review-panel')!;
superdoc.on('comments-list-change', ({ isRendered }) => {
  panel.hidden = !isRendered;
});
panel.hidden = !superdoc.addCommentsList(panel);
```

The list appears before it has loaded the document's comments and changes. To know when they have loaded, observe
`superdoc.ui.comments` and `superdoc.ui.trackChanges` and wait until both snapshots report `listStatus: 'ready'`. The
list is still loading while either is `'pending'` or `'stale'`. [Build a custom comments panel](/editor/custom-ui/comments)
and [Build a custom review panel](/editor/custom-ui/tracked-changes) cover `observe()`:

```ts
const ready = { comments: false, trackChanges: false };
const showLoading = () => panel.toggleAttribute('data-loading', !ready.comments || !ready.trackChanges);
superdoc.ui.comments.observe(({ listStatus }) => {
  ready.comments = listStatus === 'ready';
  showLoading();
});
superdoc.ui.trackChanges.observe(({ listStatus }) => {
  ready.trackChanges = listStatus === 'ready';
  showLoading();
});
```

## Verify the round trip

1. Create a comment and reply to it.
2. Resolve or reopen the thread.
3. Use the export and reopen flow from [Load and save](/editor/load-and-save-documents); the standalone examples above
   only configure comments.

The thread, replies, author, and status should remain in the file.

Use [custom comments UI](/editor/custom-ui/comments) when your application should render the thread list or composer. Use
[Document API comments](/document-api/comments) when code needs to create or update comments directly.
