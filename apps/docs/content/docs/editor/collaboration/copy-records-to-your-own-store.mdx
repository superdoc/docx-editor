An **observer** is a backend process that joins a collaboration room with a SuperDoc SDK. It reads [change records](/editor/collaboration/record-changes) as they arrive and writes them to your own storage. Your collaboration server needs no SuperDoc code.

## Before you start

Install the SDK for your language. See the [Node.js](/agents/automation/node-sdk), [Python](/agents/automation/python-sdk) or [Rust](/agents/automation/rust-sdk) guide.

The observer opens the room the same way any SDK session does. It supports these providers:

| `providerType`  | Room                   | Authentication                                                                   |
| --------------- | ---------------------- | -------------------------------------------------------------------------------- |
| `'hocuspocus'`  | `url` and `documentId` | A token for this open request: `collaborationAuth: { type: 'token', token }`.    |
| `'y-websocket'` | `url` and `documentId` | A token for this open request, as for Hocuspocus.                                |
| `'liveblocks'`  | `roomId`               | `authEndpoint` or `publicApiKey` in `collaboration`. There is no per-open token. |

The samples below use Hocuspocus. For another provider, change the `collaboration` object and the authentication.

Give the observer read-only access where your server supports it. On Hocuspocus, mark the observer's connection read-only. The [server template](/editor/collaboration/deploy-a-server#check-access) does this when its access check returns `readOnly: true`. A read-only connection writes nothing to the room, not even attribution keys. The observer makes no edits of its own.

## How the loop works

The three samples follow the same steps:

1. Join the room with `roomMode: 'join'`.
2. Take a snapshot. A session sees only the edits made after it joined, so this snapshot records the state it started from.
3. Call `changes.list({ after: cursor, waitMs: 30000, includeUpdate: true })`. The call returns as soon as a record after the cursor exists, or with no records after 30 seconds.
4. Append each record whose `id` is not stored yet. Use `id` as the primary key in your database and insert only when it is absent.
5. Replace the cursor with the one the result returns, then save it. Do this on every call, even when there are no records.
6. Take a snapshot every 250 records, every 10 minutes while the room is active, when a call returns nothing after activity, and when `truncated` is `true`.

These numbers are sample defaults. SuperDoc does not schedule snapshots for you.

## What to keep

A record's `update` is the exact Yjs update behind it, base64 encoded. Keep it when you want to inspect or audit the bytes of an edit. An [oversized record](/editor/collaboration/record-changes#oversized-records) can arrive without its `update` and with part of its text left out.

A snapshot holds the revision, the cursor, the last change id, the time, the Yjs state vector and, with `includeState`, the room's full state as a base64 Yjs update. Use snapshots, not records, to rebuild a room's state. Updates that produce no record, such as SuperDoc's own maintenance writes, are not in your record list.

SuperDoc sessions keep deleted content. Content deleted before the observer joined is in a snapshot only if your server's Yjs documents keep deleted content (garbage collection off).

## Restarts and gaps

<Callout variant='warning' title='A cursor belongs to the session that issued it'>
  Never build or compare cursors. After the observer restarts, its saved cursor comes from an earlier session. The first
  call then returns from the oldest record the new session holds, with `truncated: true`. The loop stores those records,
  adopts the new cursor and takes a snapshot. The next call is normal again.
</Callout>

Edits made while no observer was connected have no records. The new session starts empty and sees only what happens after it joins. The snapshot it takes first gives you the room's state at that point, and its state vector shows where the gap ends.

`truncated: true` also means the session dropped records before you read them, for example because the observer fell behind the session's [retention window](/editor/collaboration/record-changes#which-sessions-record). The loop takes a snapshot when it sees it.

If a call throws, for example because the connection failed, close the document, open the room again and continue from your saved cursor. Run the observer under a supervisor that restarts it when it exits.

## Push instead of poll

The SDK host also sends each batch of records as an `event.change` notification with params `{ sessionId, records }`. Pushed records carry no `update` and no cursor. When a subscriber falls behind, the SDK drops the oldest notifications and raises `NOTIFICATIONS_LAGGED`. The loop above loses nothing, because it reads records from its cursor. A record can arrive by push and by `changes.list`, so keep deduplicating on `id`. `event.remoteChange` still reports only that something changed.

In Python, `client.subscribe(capacity=256)` returns a stream with `recv(timeout=30)`, which returns `None` on timeout. In Rust, `client.subscribe()` returns a stream with `recv().await`. Both raise an error with code `NOTIFICATIONS_LAGGED` when they fall behind.

Polling with `waitMs` has no lag case, so it is the simpler loop to start with.

## Run more than one observer

Run one observer per room. Sessions that receive the same update compute the same id, including for merges and moves. Yjs can merge updates, for example while a client reconnects, and a merged update forms one record with a new id that covers the same edits. Two observers can therefore store the same edit under different ids. Do not merge their histories by id alone.

## Name versions

A named version is a pointer into your store. Keep:

```json
{
  "name": "Sent to legal",
  "revision": "48",
  "cursor": "…",
  "snapshotRef": "history/contract-123/snapshots/2026-11-05T10-15-00.000Z.json",
  "createdBy": "alex",
  "createdAt": "2026-11-05T10:15:00Z"
}
```

`revision` and `cursor` come from `changes.snapshot()`. `snapshotRef` points at the stored state. Create a version when someone saves, on a timer, or when the room goes idle.

You can also export a DOCX at that point and store it next to the pointer. See [Version history](/editor/version-history) for DOCX versions. Restoring a version in a live room is a workflow your server owns. See [Restore shared documents separately](/editor/version-history#restore-shared-documents-separately).
