Built-in content-control chrome helps someone recognize and click a field in the document. Build a custom panel when
your application needs to keep every field visible, move between them, or render a field-specific input.

This guide replaces only the field panel. SuperDoc continues to render the toolbar, document, selection, and
content-control chrome.

## Try the field workflow

The example loads a text field and a checkbox on two short pages.

1. Change **Client name**, then choose **Update**. The value changes in the document.
2. Choose **Show in document** for **Review approved**. The Editor moves to the checkbox on page 2.
3. Check **Approved**, then return to **Client name** with **Show in document**.

## Connect field state to typed mutations

The panel uses two public surfaces with different jobs:

- `ui.contentControls` supplies the observed field catalog, active field IDs, and `focus()` navigation.
- `activeEditor.doc.contentControls` supplies type-specific document mutations. This example uses `text.setValue()` and
  `checkbox.setState()`.

Each catalog item carries its `controlType`, `lockMode`, properties, current value, and mutation target. Use those values
instead of inspecting the rendered document DOM.

Keep every action disabled while a mutation is pending. A successful receipt confirms that the Document API accepted
the mutation. Confirm the updated field value before clearing the draft and reporting success.

In `superdoc@2.12.0`, the observed catalog can remain stale after a programmatic update. These examples read
`contentControls.list()` after mutations and observer notifications, ignoring older responses. A failed refresh reports
that the document changed but the panel could not refresh; it does not report the mutation as failed.

## Read active fields after selection changes

`ui.selection` and `ui.contentControls` settle independently. Read each snapshot's `status`:

| Status    | Meaning                                                                          |
| --------- | -------------------------------------------------------------------------------- |
| `pending` | The read has not settled; an empty list is an initial value.                     |
| `stale`   | A refresh is running; the snapshot contains previously settled, best-known data. |
| `ready`   | The underlying reads have settled for the current state.                         |

A ready caret selection can coexist with a stale content-controls snapshot whose `activeIds` is empty, even when
`items` lists an enclosing control. This can occur inside `onException` after a rejected keystroke in a locked field.
Empty stale IDs do not establish that the caret is outside every control. Observe the controls slice becoming ready
for current active IDs; another selection or document change can start a new refresh.

```ts
const stopObserving = ui.contentControls.observe((snapshot) => {
  if (snapshot.status !== 'ready') return;
  const activeFields = snapshot.activeIds.flatMap((id) => {
    const field = ui.contentControls.get({ id });
    return field ? [field] : [];
  });
  // Render activeFields in your application panel.
});
// Call stopObserving() when the panel is removed.
```

### Read cached context inside a rejection callback

`getSnapshot()`, `list()`, and `get({ id })` read loaded controller state synchronously. They do not synchronously
refresh the catalog or identify the cause of a rejected edit. The callback has no guaranteed lock-specific reason
or rejecting-control ID. In particular, `INVALID_CONTEXT` has several causes, and an active field describes the
selection rather than proving which control rejected an operation. See [Handle rejected edits](/editor/lifecycle-and-events#handle-rejected-edits).

For a known, unchanged catalog, compare a ready caret with cached `selectionTarget` ranges to obtain field context.
The helper below handles one unambiguous inline control in a body paragraph, strictly inside its text. It returns
`null` for unknown freshness, missing targets, non-caret selections, other stories, multi-block controls, mismatched
coordinate spaces, boundary carets, or multiple enclosing controls. An omitted story means body; an omitted coordinate
space means visible.

<include>../../../../snippets/editor/cached-control-at-caret.ts</include>

Call `cachedControlAtCaret(ui.contentControls, ui.selection.getSnapshot(), catalogKnownCurrent)` inside your rejection
handler. Set `catalogKnownCurrent` only when your integration knows the loaded IDs and ranges have not changed since
a settled catalog was obtained. A previously ready snapshot alone cannot guarantee that after later edits. Leave it
false if freshness is unknown. A returned field's `lockMode` supplies context for that field; it is not causal proof.
For authoritative current field state, refresh through the Document API or observe a ready slice outside the
synchronous callback.

### Shared editing

The same per-slice readiness and generic rejection contract applies in a supported V2 shared document. Content-control
state refreshes when remote document changes are observed, so cached ranges also require freshness against remote
edits. Each client's `activeIds` follows its own selection; another client's caret does not become locally active.
A rejected keystroke inside a content-locked inline field leaves shared text unchanged on both clients.

## React to a field click

`ui.contentControls.onClick` reports each click inside a content control. When controls are nested, `target` is the
innermost one:

```ts
const stopClicks = ui.contentControls.onClick(({ target }) => {
  // Select target.id in your panel.
});
// Call stopClicks() when the panel is removed.
```

Use it instead of the slices when the click itself is the event. Clicking the field the caret is already in leaves
`activeIds` unchanged, so `observe` and `observeActivePath` report nothing; `onClick` reports every click. The payload
is `{ target, source: 'pointer' }`, where `target` carries the control's `id`, `tag`, `alias`, `controlType`, and
`scope`.

This replaces the `content-control:click` instance event and the `onContentControlClick` configuration callback. Both
still work and are deprecated for removal in v3.0.

## Highlight a field from your panel

Use `highlight()` when a pointer enters a panel row, and `clearHighlight()` when it leaves:

```ts
row.addEventListener('pointerenter', () => {
  void ui.contentControls.highlight({ id: control.id });
});
row.addEventListener('pointerleave', () => ui.contentControls.clearHighlight());
```

The browser Editor highlights the control's text across paragraphs and table cells without moving focus, selection,
or scroll. One highlight is active at a time. A successful request replaces it; a failed request preserves it.
The result is `{ success: true }` or `{ success: false, reason }`. Unknown IDs, empty controls, and unavailable Editors
fail explicitly. Offscreen text appears highlighted when its page mounts. Clearing cancels pending requests, and
opening another document clears the highlight. This also works in viewing mode and does not change saved document content.

The default background is yellow (`#ffff00`). Set a CSS variable on your Editor wrapper to override it:

```css
.contract-editor {
  --sd-content-controls-highlight-bg: #b9e8ff;
}
```

No JavaScript color option is needed. Removing the variable restores the yellow default.

## Render the field type you support

This panel handles text fields and checkboxes. Date, choice, rich-text, and repeating controls have their own operations.
Render an input only when its `controlType` matches an operation your panel implements. Disable content mutations for
`contentLocked` and `sdtContentLocked` fields, and still inspect every mutation receipt.

Use [Content controls](/editor/content-controls) to create template fields, fill repeated values, and choose lock modes.
The [Document API reference](/document-api/reference/content-controls/) lists every content-control type and operation.
