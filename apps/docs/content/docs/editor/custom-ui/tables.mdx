A DOCX table does not require custom UI. Build these controls only when your application needs actions outside the
document that follow the active cell, such as **Add row** in an application toolbar. Use `ui.tables` to read that
selection context and `ui.commands` to run actions against it.

If your application already has an explicit table target, use the
[Document API tables reference](/document-api/reference/tables/) instead. To give a table one of Word's built-in
styles, see [Apply a Word table style](/document-api/table-styles).

## Render command state, not assumptions

Each table command reports whether it is supported and enabled. Outside a table, contextual actions fail closed with
`table-context-unavailable`. In viewing mode, mutations report `document-readonly`.

Use `getState()` for the initial render and `observe()` for later selection, mode, and capability changes. Still inspect
the result from `executeAsync()`. Context can change between rendering a button and clicking it.

The routed table command family includes inserting or deleting rows and columns, deleting a table, merging cells,
splitting a cell, and removing borders. Add only the controls your workflow needs. Do not render every catalog command
as a toolbar.

## Keep context tied to selection

`ui.tables.getContext()` returns the current table ID, row and column indices, cell ID, and dimensions when the host can
resolve them. Treat that snapshot as presentation state. Do not cache it as a durable mutation target or derive
Document API mutation targets from painted DOM attributes.

## Identify painted rows for overlays

Each painted `.superdoc-table-fragment` exposes an opaque `data-table-id`. Each painted cell exposes
`data-row-index`, the decimal, zero-based index of its logical owner row. Together with the editor/document instance,
these identify a row for hover outlines and hit testing. Compare table IDs as strings; do not decode them or parse
`data-layout-block-ref`.

The V2 browser currently exposes this painted cell surface for body tables, including nested body tables. Other
stories do not yet expose the same surface. Pass the mount element belonging exclusively to one editor as
`editorRoot`; a shared ancestor containing several editors can combine unrelated rows with equal IDs.

Resolve the painted rectangle at the pointer, then collect cells owned by its nearest table. Inspect rectangles rather
than relying on `elementFromPoint().closest()`: decorative cells may ignore pointer events, and nested text may be
painted outside its nested cell's DOM subtree. Reverse DOM order gives nested cells priority over their outer cell:

```ts
function paintedRowAtPoint(editorRoot: HTMLElement, clientX: number, clientY: number) {
  const cells = Array.from(editorRoot.querySelectorAll<HTMLElement>('[data-row-index]'));
  const cell = cells.reverse().find((candidate) => {
    const rect = candidate.getBoundingClientRect();
    return clientX >= rect.left && clientX < rect.right && clientY >= rect.top && clientY < rect.bottom;
  });
  const table = cell?.closest<HTMLElement>('[data-table-id]');
  if (!cell || !table) return;
  const pieces = cells.filter(
    (candidate) =>
      candidate.dataset.rowIndex === cell.dataset.rowIndex &&
      candidate.closest<HTMLElement>('[data-table-id]')?.dataset.tableId === table.dataset.tableId,
  );
  return {
    tableId: table.dataset.tableId,
    rowIndex: cell.dataset.rowIndex,
    rectangles: pieces.map((piece) => piece.getBoundingClientRect()),
  };
}
```

One row can have several painted pieces across pages. Split rows and repeated headers keep their original row index.
A vertically merged cell, including its page continuation, belongs to its starting row throughout its rectangle;
a horizontal span remains one cell. Nested tables have their own table IDs, so use the nearest enclosing table when
grouping cells. There is no required row wrapper. These markers preserve the separate accessibility table and focus
behavior. Call this lookup for points within the editor's visible viewport; keep host overlays `pointer-events: none`
so they preserve editor interaction.

The table ID is scoped to one mounted editor/document and story. Row mapping survives scrolling, page unmount/remount,
repaint, repagination, and text or formatting edits that preserve table structure and source ownership. DOM elements
can be replaced on any paint; only mounted page content has markers. Reacquire markers after structural edits,
including inserting or removing blocks before a table, table/row insertion, deletion, reorder, merge or split,
document replacement, save/reopen, or Word round trips. IDs are not synchronization identifiers across peers.

`data-table-id` is an overlay identifier, not a Document API `table.nodeId` or mutation locator. An optional
`data-source-node-id` does not change that contract. Use `ui.tables` or Document API discovery for commands. Durable
table addresses across structural edits and reopen are tracked separately in SD-5000; these markers do not provide
durable row addresses.

## Verify the controls

To initialize a dimension dialog for an explicit table, read `editor.doc.tables.getProperties({ nodeId })`.
V2 returns `rows` with zero-based `rowIndex`, optional `heightPt`, and optional `heightRule` (`atLeast`, `exact`, or
`auto`), and `columns` with zero-based `columnIndex` and optional `widthPt`. Both sizes are authored points,
normalized to the nearest twip (1/20 point), rather than measured layout sizes. Column widths come from the saved
table grid, rather than cell preferred widths or AutoFit measurements. Existing table-level `preferredWidth` uses twips.
Export can normalize grids to reconcile a fixed preferred table width; reopening reports the grid stored in that export.
Use fixed layout with `preferredWidthType: 'auto'` when authoring column widths independently of an overall table width.

An omitted size means no direct authored value; an explicit zero remains `0`. An omitted `heightRule` remains absent
even when a height is stored. Preserve that distinction in the dialog instead of assuming a rule. For example,
`{ rowIndex: 0 }` differs from `{ rowIndex: 0, heightPt: 0, heightRule: 'auto' }`, and `{ columnIndex: 0 }` differs
from `{ columnIndex: 0, widthPt: 0 }`. The array containers are optional in the public contract for adapter compatibility.

Place the caret in the milestone table, add a row, delete a row, and choose **Download DOCX**. Outside the table, both row buttons should disable
with a contextual reason.
