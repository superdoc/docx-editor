`onReady` means the document is available for queries and export. `onEditorUpdate` reports document edits, not cursor
movement or pagination. Downloading a copy does not save changes to your application, so it does not clear the
**Unsaved changes** status.

In a collaborative room, `onEditorUpdate` also fires when another collaborator's change reaches this editor. The event's
`isRemote` field is `true` for those changes and `false` for edits, undo, and redo made here. Skip `isRemote` events
when the handler writes back to your application or marks this user's changes as unsaved. A remote event always
reports `surface: 'body'` because the room does not say which part of the document changed.

## Choose where to listen

The `SuperDoc` instance reports the instance: its lifecycle, failures, the document lock, the collaboration session,
and the built-in UI's own chrome. Everything about one area of the document or the view belongs to that area of
[`superdoc.ui`](/editor/custom-ui/controller-setup), where `getSnapshot()` and `observe()` report state, `onChange()`
reports committed changes, and `onX()` reports an interaction.

| Your question                                                 | Where to listen                                                   |
| ------------------------------------------------------------- | ----------------------------------------------------------------- |
| Is the document open, and did opening it fail?                | `onReady`, `onException`                                          |
| Is the document locked, and is collaboration still connected? | `onLocked`, `onCollaborationConnectionChange`                     |
| Did the built-in comments list appear or disappear?           | `onCommentsListChange`                                            |
| What changed in the document?                                 | `superdoc.ui.document.onChange()`                                 |
| What is the zoom, the mode, or the undo depth right now?      | `superdoc.ui.zoom`, `superdoc.ui.document`, `superdoc.ui.history` |

An instance event is deprecated once its `superdoc.ui` replacement reports everything the event reported. Deprecated
events keep working until SuperDoc 3.0.

| Deprecated event                                        | Replacement                                                                                                    |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `zoomChange` and `onZoomChange`                         | [`superdoc.ui.zoom.observe()`](/editor/custom-ui/zoom-and-document-state#build-zoom-and-download-controls)     |
| `document-mode-change`                                  | [`superdoc.ui.document.observe()`](/editor/custom-ui/zoom-and-document-state#build-zoom-and-download-controls) |
| `list-definitions-change` and `onListDefinitionsChange` | `onEditorUpdate` and `doc.lists.list()`                                                                        |

The document snapshot reports the mode. SuperDoc 2 never emits `list-definitions-change`.

`history-change` stays on the instance: it reports every open document with its `documentId`, while
`superdoc.ui.history` follows the active document.

## Handle rejected edits

The browser Editor reports a rejected keyboard edit through `onException` (or the `exception` event),
with `code: 'edit-rejected'`. Your application decides whether and how to present a message. SuperDoc
adds no error message to the document UI. Each independent rejected attempt produces its own event;
a proven no-op at a document or body/table boundary produces none.

The payload's `error` is unknown: narrow it to an `Error` before reading `message` or `cause`.
The optional `error.cause` contains diagnostic codes such as `failureSource`, `reason`, `inputKind`,
and `editableCommandKind`. `failureSource: 'shell'` identifies a host dispatch rejection, while
`'receipt'` identifies a Document API mutation failure. These values identify the originating layer,
not severity. Cause fields and reason values are diagnostic details, not a typed, exhaustive public
contract; tolerate absent fields and unfamiliar reasons. Use the exception code for application routing
and avoid treating a diagnostic reason as a permanent capability check.

The normalized cause excludes raw document text and receipt messages. Review other error details
before sending them to your logging or support system.

For a rejected edit inside a locked content control, the callback does not guarantee a lock-specific reason or
rejecting-control ID. Selection and content-control snapshots can have different readiness states in the same
callback. Use the [field-state and cached-context guidance](/editor/custom-ui/content-controls#read-active-fields-after-selection-changes)
for ready active IDs and bounded synchronous lookup, including shared editing. Treat cached field context as
context rather than evidence of the rejection's cause.

## Release what you own

Call `unmountEditor()` when the owning route or component unmounts. It removes the button listener and calls
`destroy()`. The React Quickstart's `SuperDocEditor` component handles its own Editor cleanup.

For a temporary panel, keep the function a `superdoc.ui` subscription returns and call it when the panel closes. An
instance event uses `on()` and `off()` with the same function. This fragment assumes the ready `superdoc` instance
from the example above:

```ts
const stopZoom = superdoc.ui.zoom.observe(({ value }) => {
  console.log('Zoom:', value);
});
// When the panel closes:
stopZoom();
```

## Export recent Interaction History

The browser Editor keeps a bounded **Interaction History** in memory by default. When an edit looks wrong,
your application can request a snapshot without waiting for an exception:

```ts
const history = superdoc.diagnostics.getSnapshot();
const report = JSON.stringify(history);
// Let the customer review and share the report through your bug-report flow.
superdoc.diagnostics.clear();
```

The history records recent input attempts, commands, mutation receipts, selection changes, render progress,
and lifecycle failures. Collaboration sessions also record remote changes observed by this browser.
A snapshot is detached from the running recorder; capturing it does not query the worker or document.
You can also request one inside `onException`.

Configure retention when creating the Editor:

```ts
const superdoc = new SuperDoc({
  selector: '#editor',
  diagnostics: {
    history: {
      enabled: true,
      maxEvents: 500,
      maxBytes: 1_048_576,
      captureContent: false,
    },
  },
});
```

These are the defaults. The oldest events are removed when either limit is reached. `maxEvents` accepts
1–10,000; `maxBytes` accepts 1–16,777,216 and measures retained serialized UTF-16 payloads, excluding object
overhead. Invalid limits use the defaults. Individual events and nested payloads are also capped; snapshots
report eviction, truncation, and capture-failure counts. Set `enabled: false` to disable capture.

By default, the recorder selects metadata fields and excludes document text and error messages.
`captureContent: true` allows bounded text carried by observed events and API calls; treat those reports
as document content. Metadata can include document and transaction identifiers, so review reports before sharing.
This recorder does not upload or persist reports. Capture stops when the instance is destroyed; the history
belongs to that instance and does not survive a page reload. Capture failures are isolated from editor operations.

History is diagnostic evidence, not a complete replay or audit log. Selection events may be coalesced,
older events may be evicted, and each collaboration peer records its own observation order.
